# AUDIT REPORT — My_Helper_2

**Aplikacja SaaS dla salonów piękności**
**Data: 14 marca 2026 | Autor: Claude Code Audit Agent**

## 1. Podsumowanie

My_Helper_2 to rozbudowana aplikacja SaaS typu Booksy. Stack: Next.js 15 + TypeScript strict + Drizzle ORM + PostgreSQL (Neon) + better-auth + Stripe. Projekt: 44 tabele, ~160 endpointów API, pełna infrastruktura testowa (Vitest + Playwright).

**Audit zidentyfikował 48 problemów w 4 kategoriach.**

| CRITICAL | HIGH | MEDIUM | LOW |
|----------|------|--------|-----|
| 13 | 17 | 13 | 5 |

**Najkrytyczniejszy problem: 91 endpointów API bez autentykacji — każdy z dostępem do internetu może czytać i modyfikować dane dowolnego salonu.**

## 2. Bezpieczeństwo

### 2.1 Brak autentykacji na API (CRITICAL)

91 z ~160 endpointów API nie sprawdza tożsamości użytkownika. Każdy kto zna URL może: czytać dane klientów salonów, modyfikować wizyty, usunąć salon, potwierdzać fałszywe płatności.

| # | Severity | Problem | Akcja |
|---|----------|---------|-------|
| 1 | **CRITICAL** | DELETE /api/salons — każdy może usunąć dowolny salon | Dodaj requireAuth() + requireAdmin() |
| 2 | **CRITICAL** | POST /api/salons — tworzenie salonów bez weryfikacji | Dodaj requireAuth() |
| 3 | **CRITICAL** | /api/deposits/confirm — potwierdzanie płatności bez auth | Dodaj requireAuth() + weryfikacja ownera |
| 4 | **CRITICAL** | 91 GET endpointów zwraca dane biznesowe bez auth | Centralne middleware auth |
| 5 | **CRITICAL** | Tylko 2 z 162 endpointów sprawdza rolę użytkownika | RBAC middleware (owner/employee/client) |
| 6 | **CRITICAL** | Endpointy CRON z opcjonalnym CRON_SECRET | Wymuś CRON_SECRET na wszystkich cron routes |

### 2.2 Inne problemy bezpieczeństwa

| # | Severity | Problem | Akcja |
|---|----------|---------|-------|
| 7 | MEDIUM | PII w logach — numery telefonów, emaile, SQL queries w console.log | Structured logging, usuń PII |
| 8 | MEDIUM | Brak rate limitingu na API | Vercel rate-limit middleware |
| 9 | MEDIUM | 254 instancji console.log w production code | ESLint no-console: error |
| 10 | LOW | Brak CORS whitelist na API routes | Dodaj CORS headers |

### 2.3 Co działa dobrze

- Env vars: .env.local w .gitignore, brak hardcoded secrets
- Drizzle ORM: parametryzowane queries, brak SQL injection risk
- Stripe webhook: poprawna weryfikacja signature
- File uploads: sanityzacja nazw, whitelist MIME types, limit 5MB
- Session: 15-min timeout, better-auth poprawnie skonfigurowany

## 3. Baza danych i performance

### 3.1 N+1 Queries (CRITICAL)

Dwa endpointy wykonują zapytania do bazy w pętli — przy dużej ilości danych mogą generować setki zapytań zamiast jednego.

| # | Severity | Problem | Akcja |
|---|----------|---------|-------|
| 11 | **CRITICAL** | Newsletter send: INSERT w pętli (254 odbiorców = 254 queries) | Batch insert: db.insert().values([...array]) |
| 12 | **CRITICAL** | Push reminders cron: SELECT + UPDATE w pętli na każdy appointment | Prefetch z inArray() + batch update |

### 3.2 Brakujące indeksy i constraints

| 14 | **CRITICAL** | Brak indeksu na appointments.serviceId (30+ JOINów) | CREATE INDEX |
| 15 | **CRITICAL** | Brak composite appointments(employeeId, startTime) — available-slots | CREATE INDEX |
